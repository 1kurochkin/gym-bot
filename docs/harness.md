# Харнесс для агентов

## 12. Репозиторий и харнесс для агентов

Цель: любая новая сессия агента (без памяти об этом чате) за пару минут понимает, что это за проект, где правила и что делать дальше. Принцип — минимум структуры, которая реально читается и обновляется; ничего не создаётся «на вырост».

```
CLAUDE.md              индекс и правила (≤ 150 строк)
STATUS.md              текущий этап, что сделано, следующий шаг, известные проблемы
.specs/                что делает бот (продуктовые спецификации)
  README.md            индекс спецификаций + карта «раздел брифа → файл»
  product.md           обзор, скоуп, сценарии (разделы 1, 2, 5)
  program-format.md    шаблон программы (раздел 4) + JSON Schema, сгенерированная из zod
  warmup.md            алгоритмы и контрольные примеры (раздел 6)
  data-model.md        раздел 7
  export.md            раздел 8
  nfr.md               раздел 9
  roadmap.md           этапы и критерии приёмки (раздел 10)
  decisions.md         журнал решений (раздел 11)
docs/                  как устроен код и репозиторий
  README.md            индекс документации
  architecture.md      технический гайд (разделы 3 и 13)
  harness.md           этот раздел: харнесс для агентов (раздел 12)
  runbook-restore.md   восстановление БД из дампа
  adr/
    0000-template.md
    0001-hosting-and-db.md
    0002-units-lb.md
    0003-warmup-by-work-weight.md
    0004-timezone-iana.md
    0005-llm-optional-with-confirmation.md
    0006-code-architecture.md
.claude/
  settings.json        хуки
tests/fixtures/        контрольные примеры как данные
```

**`CLAUDE.md`** — входная точка: что за продукт (2–3 предложения), карта «где что лежит», команды (`dev`, `check`, `deploy`), правила репозитория и Definition of Done. Правила, которые стоит зафиксировать сразу:

- Спецификация — источник истины. Изменилось поведение → сначала правка в `.specs/`, потом код, в одном коммите.
- Новое техническое решение, которое дорого откатить → новый ADR (контекст, решение, альтернативы, последствия; полстраницы).
- `src/core/` — только чистые функции, без I/O; всё I/O за портами в `src/ports/`, реализации в `src/adapters/`.
- Контрольные примеры из спецификации живут в `tests/fixtures/` и тестируются. Пример в спеке, которого нет в фикстурах, считается багом.
- Все веса в lb, все даты в UTC плюс `local_date`.
- В конце сессии обновить `STATUS.md`.

**`STATUS.md`** — самый полезный файл для длинного проекта: при сбросе контекста агент читает его первым и продолжает с того же места. Формат: текущий этап, чеклист этапа, последние решения, следующий конкретный шаг, известные проблемы.

**ADR** — не оверинжиниринг, если держать их короткими. Они отвечают на вопрос «почему так», который из кода не восстановить (почему Supabase, а не Cloudflare; почему IANA-зона, а не UTC−4). Статусы: `proposed` / `accepted` / `superseded by 000X`.

**`.specs/`** — этот документ, разрезанный по темам. Так агент грузит только нужный кусок, а не всю спецификацию. После переноса в репозиторий источником истины становится репозиторий; этот документ остаётся как исходный бриф.

**Хуки (2 штуки, не больше)**

- `PostToolUse` на правку `.ts`: быстрый typecheck и lint изменённого файла. Ошибка возвращается агенту сразу, а не в конце.
- `Stop`: `deno task check` (fmt + lint + typecheck + tests + architecture test). Агент не закончит работу с красными тестами.

**Skills.** Первый скилл — `/deploy` (`.claude/skills/deploy/`): логин в Supabase CLI, `.env.prod`, секреты, миграции, функция, webhook. Работа с секретами — только через `prod.sh`, который не печатает значения.

**MCP и остальные skills — пока не нужны.** Заводить их стоит, когда появится повторяющаяся задача, а не заранее. Кандидаты на потом: skill «добавить новый тип упражнения или схему разминки» (схема → фикстуры → core → features → экспорт), когда это придётся делать второй раз; официальный MCP-сервер Supabase для просмотра данных и миграций, если отладка через SQL-редактор в дашборде станет утомительной. Пустые папки на будущее только создают шум.

### 12.4. Хуки

`.claude/settings.json`:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/hooks/check-file.sh" }]
      }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": ".claude/hooks/stop-check.sh" }] }
    ]
  }
}
```

`.claude/hooks/check-file.sh` — после правки `.ts` файла: typecheck проекта и lint файла. При ошибке код выхода 2, и вывод уходит агенту, чтобы он сразу исправил.

```bash
#!/usr/bin/env bash
f=$(jq -r '.tool_input.file_path // empty')
[[ "$f" == *.ts ]] || exit 0
out=$( (deno check "$f" && deno lint "$f") 2>&1 ) || { echo "$out" | tail -40 >&2; exit 2; }
```

`.claude/hooks/stop-check.sh` — перед завершением работы полный `deno task check`. Проверка `stop_hook_active` не даёт хуку зациклиться, если агент уже чинит ошибки по его сигналу.

```bash
#!/usr/bin/env bash
[[ $(jq -r '.stop_hook_active') == "true" ]] && exit 0
out=$(deno task check 2>&1) || { echo "$out" | tail -40 >&2; exit 2; }
```

Оба скрипта нужно сделать исполняемыми (`chmod +x`), а `jq` должен быть установлен. Если typecheck всего проекта на каждую правку станет медленным, в первом хуке оставить только lint, а typecheck перенести в `Stop`.

### 12.5. Порядок внедрения

1. Этап 0: `CLAUDE.md`, `STATUS.md`, `.specs/` (этот документ, разрезанный по разделам), ADR 0001–0005, фикстуры разминки.
2. Хуки — сразу после появления `deno task check`, чтобы было что запускать.
3. Skill или MCP — только когда задача повторится второй раз.
