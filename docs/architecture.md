# Архитектура

## 3. Стек и архитектура

**Решение (28.09, ADR-0001 accepted):** Supabase — Edge Functions + Postgres, бесплатный план.

| Слой | Выбор | Комментарий |
|---|---|---|
| Язык | TypeScript | Edge Functions работают на Deno, тулчейн тоже Deno (`deno test`, `deno lint`, `deno fmt`), npm-пакеты через `npm:`. Архитектура кода — раздел 13 |
| Бот-фреймворк | grammY | Официально поддерживает Deno и Supabase Edge Functions: `webhookCallback(bot, "std/http")` |
| Хостинг | Одна Supabase Edge Function `bot` = webhook для всех команд | Бесплатно до 500 000 вызовов в месяц — это на порядки больше, чем нужно |
| БД | Supabase Postgres + Drizzle ORM (`npm:drizzle-orm`, `npm:postgres`) | Подключение через пулер Supavisor в режиме transaction (порт 6543, `prepare: false`) |
| Миграции | `supabase/migrations/*.sql` (генерируются из схемы Drizzle) | Применяются `supabase db push` |
| Экспорт | Библиотека `.xlsx`, работающая в Deno (exceljs или SheetJS через `npm:`), проверить на этапе 4 | Файл собирается в памяти и отправляется документом |
| Валидация | zod (+ генерация JSON Schema для LLM) |  |
| LLM (фаза 2) | DeepSeek через OpenAI-совместимый SDK | Провайдер меняется переменной окружения |
| Планировщик | GitHub Actions `schedule` | Ежедневный бэкап БД (он же защита от засыпания) |
| Расчёт разминки | Чистая функция в TS, без LLM | Детерминированно, покрыто тестами |

**Особенности Supabase, которые нужно учесть в реализации**

1. **Проверка JWT.** По умолчанию Edge Function требует JWT Supabase, а Telegram его не присылает. Функцию `bot` нужно деплоить с `--no-verify-jwt` (или `verify_jwt = false` в `supabase/config.toml`). Защиту обеспечивает проверка заголовка `X-Telegram-Bot-Api-Secret-Token` и проверка доступа пользователя (раздел 9).
2. **Засыпание проекта.** Бесплатный проект ставится на паузу после 7 дней без активности в БД; проект потом надо будить в дашборде. Защита: ежедневный бэкап (п. 3) сам подключается к БД, а для надёжности тот же workflow вызывает эндпоинт `/health`, который делает лёгкий запрос в БД. Внутренний `pg_cron` для этого не использовать: нет гарантии, что он считается внешней активностью.
3. **Нет автоматических бэкапов на бесплатном плане.** Решение — свой бэкап в два слоя:
    - **Ежедневный дамп БД в Telegram.** GitHub Actions `backup.yml` раз в сутки делает `supabase db dump` (схема и данные отдельно, строка подключения — в GitHub Secrets), сжимает в `.sql.gz` и отправляет файлом через Bot API (`sendDocument`) в личный чат владельца с ботом. Получатель задаётся отдельным секретом `BACKUP_CHAT_ID` (только администратор) и не зависит от списка пользователей `ALLOWED_USER_IDS`: дамп содержит данные всех пользователей, поэтому другим пользователям он не отправляется никогда. Файл видит только владелец, Telegram хранит его бессрочно. Данных мало, дамп будет весить килобайты (лимит Bot API — 50 МБ). Репозиторий публичный, поэтому дамп **никогда** не коммитится и не сохраняется как артефакт workflow: артефакты публичного репозитория может скачать любой пользователь GitHub. Если понадобится вторая копия — только зашифрованная (`age`, в репозитории лежит лишь публичный ключ, приватный — у владельца).
    - **Миграции в git.** Схема восстанавливается из `supabase/migrations/`, даже если дамп схемы потерян.

    **Восстановление** описано в `docs/runbook-restore.md`: создать проект (или `supabase start` локально), применить миграции, залить данные `psql < data.sql`. Проверить процедуру один раз на этапе 0 и затем раз в квартал: бэкап, который ни разу не восстанавливали, бэкапом не считается.
4. **Лимиты функции.** Время выполнения на бесплатном плане ограничено (порядка 150 с на запрос), для бота и экспорта с запасом. Потребление CPU при экспорте всё равно замерить на этапе 4.
5. **Холодный старт.** У Edge Functions он небольшой, но есть. Держать бандл лёгким: не тянуть тяжёлые зависимости в путь обработки кнопок, импортировать модули экспорта и LLM динамически (`await import(...)`) только когда они нужны.
6. **Регион функции.** Edge Function запускается в регионе, ближайшем к вызывающему. Webhook Telegram приходит из Европы, и без закрепления функция работала бы далеко от БД (`us-east-2`): ~150–200 мс на каждый запрос к базе, загрузка состояния — секунды, grammY отвечал 500 по своему таймауту 10 с, и Telegram повторял апдейты. Поэтому webhook регистрируется с `?forceFunctionRegion=<регион БД>` (`FUNCTION_REGION` в `.env.prod`); фактический регион — в заголовке ответа `x-sb-edge-region`. Второе следствие пулера Supavisor (transaction mode): клиент Postgres работает без prepared statements и без pipelining (`max_pipeline: 0`) — несколько запросов пачкой по одному соединению пулер обрабатывал с потерей ответа, и апдейт висел до таймаута. В логах функции на каждый апдейт — время этапов (доступ, загрузка, автомат, запись, отправка) и вызовов Telegram API, без данных пользователя.

**Как бот ощущается быстрым**

- `answerCallbackQuery` сразу после нажатия кнопки, до записи в БД: убирает «часики».
- Редактировать текущее сообщение (`editMessageText`), а не присылать новое.
- Одна транзакция на шаг, без лишних чтений: сессия и данные текущего упражнения загружаются одним запросом.
- Разминка считается локально, без обращения к БД.

Хранилище спрятано за интерфейсами репозиториев (`ProgramRepo`, `WorkoutRepo`, `SettingsRepo`), чтобы смена провайдера затрагивала один модуль. Отвергнутые альтернативы (Cloudflare Workers + D1, Firebase, VPS) описаны в ADR-0001.

**Схема работы**

```
Telegram ──webhook──▶ Edge Function "bot" (grammY, Deno)
                         │
                         ├── ядро: чистая логика и автомат диалога
                         ├── Postgres (Drizzle через пулер Supavisor)
                         ├── генерация .xlsx — этап 4, по команде /export, динамический импорт
                         └── DeepSeek — фаза 2, динамический импорт

GitHub Actions (cron, ежедневно) ──▶ дамп БД → .sql.gz в личный чат Telegram, затем /health
```

**Состояние диалога.** Функция stateless, поэтому текущий шаг (активная тренировка, текущее упражнение, что ждём на вводе) хранится в БД, а не в памяти.

**Где что в репозитории** (до уровня папок; подробнее о слоях `src/` — §13.4)

| Папка | Что там |
|---|---|
| `supabase/` | Конфиг проекта (функция `bot` без проверки JWT), SQL-миграции, точка входа Edge Function |
| `src/` | Код приложения по слоям |
| `tests/` | Тесты и контрольные примеры спецификаций |
| `.github/workflows/` | CI (`deno task check` на каждый push) и ежедневный бэкап |
| `docs/` | Этот гайд, ADR, runbook восстановления |

## 13. Архитектура кода

**Решение (28.09, ADR-0006):** функциональное ядро и императивная оболочка, диалог как явный конечный автомат, структура по фичам поверх доменного ядра, тулчейн Deno.

> Этот раздел описывает принципы и инварианты, а не конкретные файлы и функции: код меняется, идея — нет.
> Где что лежит, агент находит поиском; пути в документах допускаются только до уровня слоя
> (`src/core/`, `src/adapters/` …) и проверяются тестом ссылок.

### 13.1. Functional core, imperative shell

Почти вся ценность бота в чистой логике: разминка, округление под блины, ротация дней, чередование 100/70, переходы диалога. Ввод-вывод (Telegram, Postgres, LLM) тонкий. Поэтому код делится на две части:

- **Ядро** — чистые функции над обычными данными: без I/O, без чтения текущего времени, без знания о Telegram и БД. Тестируется без моков: вход → выход.
- **Оболочка** — принимает апдейт, загружает состояние, вызывает ядро, применяет эффекты (запись в БД, ответ в Telegram).

**Не ООП.** Функция stateless и живёт один запрос, долгоживущих объектов с поведением нет. Иерархии классов упражнений не будет. Вариативность — через размеченные объединения (discriminated union) и таблицу стратегий: новый тип упражнения — новая ветка объединения и одна функция, а исчерпывающий `switch` заставит компилятор показать все места, где ветку забыли обработать.

Иллюстрация идеи (не API проекта):

```ts
const warmupByLoadType = {
  barbell: stepsFromWorkWeight,
  weighted_bodyweight: stepsFromAddedWeight,
  reps_only: () => [],
};
```

**Объекты — только на краю**, и то как фабрики-замыкания, а не классы. Зависимости передаются явно через composition root, без DI-контейнеров и декораторов. Классы допустимы только там, где их требует библиотека.

### 13.2. Диалог как конечный автомат

Самая сложная часть бота — диалог тренировки (день → вес → разминка → подходы → комментарий → следующее упражнение, плюс отмена, возобновление, пропуск, замена). Вся его логика — одна чистая функция перехода:

> (состояние, событие, контекст) → (новое состояние, эффекты)

- **Состояние** — шаг диалога и всё, что нужно помнить между сообщениями; хранится в БД, функция stateless.
- **Событие** — то, что сделал пользователь, уже переведённое из апдейта Telegram (выбрал день, ввёл повторения).
- **Контекст** — заранее загруженные данные и текущее время, поэтому функция перехода ничего не читает сама.
- **Эффекты** — что сделать после: записать подход, сохранить настройки, показать экран.

**Цикл обработки апдейта в оболочке:**

1. Только личные чаты и мгновенный `answerCallbackQuery` (адаптер); проверка доступа — владелец из конфигурации, участник из БД или вход по приглашению (.specs/product.md → US-9); отсечение повторного `update_id` (идемпотентность).
2. Фича переводит нажатие или текст в событие.
3. Состояние и контекст загружаются одним запросом.
4. Функция перехода.
5. Одна транзакция: эффекты записи + новое состояние.
6. Отрисовка экрана (`editMessageText` или новое сообщение).

Что это даёт: возобновление тренировки бесплатно (состояние всегда в БД); сценарии приёмки тестируются как последовательность событий без Telegram; новая ветка диалога — новый шаг автомата, а не новый хендлер с дублированной логикой.

Не используются: плагин conversations из grammY (в serverless переигрывает историю, сложно отлаживать) и XState (лишний вес и абстракция для автомата из десятка состояний).

### 13.3. Отображение и кнопки

- **Экраны — чистые функции** из данных экрана в текст и кнопки. Тексты сообщений живут рядом с фичей, а не разбросаны по хендлерам.
- **Язык.** Ядро не пишет текстов: в данных экрана только значения и коды (ошибки программы, подпись часового пояса). Экран получает язык пользователя и берёт фразы из словаря своей фичи; английский словарь обязан иметь те же ключи, что русский, иначе не пройдёт typecheck. Числа, даты и склонения — общие помощники в `src/features/` (.specs/product.md → «Язык интерфейса»).
- **Кодек `callback_data`.** В Telegram лимит 64 байта на кнопку, поэтому JSON в кнопки не кладётся: короткий код действия плюс номер шага сессии. Декодированное действие проверяется схемой. Нажатие на кнопку от устаревшего шага не создаёт дубль: бот убирает у старого сообщения клавиатуру.

### 13.4. Слои и правило зависимостей

| Слой | Что в нём | Может зависеть от |
|---|---|---|
| `src/shared/` | Общие примитивы (результат с ошибкой, утилиты) | — |
| `src/core/` | Чистая доменная логика и автомат диалога | shared, zod |
| `src/ports/` | Интерфейсы внешнего мира (хранилище, UI, время, геолокация…) | core, shared |
| `src/features/` | Вертикальные срезы: апдейт → событие, данные экрана → текст и кнопки | core, ports, shared |
| `src/adapters/` | Реализации портов: Postgres, Telegram, внешние API | core, ports, shared |
| `src/app/` | Composition root и HTTP-роутинг; единственное место, где встречаются адаптеры | всё |

Точка входа Edge Function — тонкая обёртка над `src/app/`. Инфраструктура: миграции и конфиг Supabase — в `supabase/`, workflow — в `.github/workflows/`, контрольные примеры спецификаций — в `tests/fixtures/`.

**Правило проверяется автоматически**: architecture test проходит по импортам и падает при нарушении. Он входит в `deno task check`, поэтому агент не сможет незаметно протащить запрос к БД в расчёт разминки.

**Почему это масштабируется:** новая фича — новый срез, ядро не трогается; второй интерфейс (например, веб-дашборд) переиспользует ядро и порты целиком; смена БД затрагивает один адаптер.

### 13.5. Соглашения

- **Типы данных — из zod-схем.** Тип данных объявляется схемой и выводится из неё (`z.infer`); рукописные `type`/`interface` для данных не пишем. Объединения — `z.discriminatedUnion`, неизменяемость — `.readonly()`. Схема заодно проверяет данные на границах: строки БД, `callback_data`, конфиг.
- **Перечисления — `z.enum`.** Значения берутся из схемы (`.enum`, `.options`), а не повторяются строковыми литералами. Подмножество — `.extract([...])`, расширение — новый `z.enum` из `.options` базового.
- **Исключения из правила** — обычные TS-типы: порты с поведением, наборы зависимостей и дженерик результата. Схема функции ничего не проверяет.
- **Ошибки.** Ядро не бросает исключения, а возвращает результат с типизированной причиной (причины — тоже `z.enum`). Исключения — только в оболочке, для настоящих сбоев (БД недоступна).
- **Единицы.** Веса — branded-тип через `.brand()`: нельзя случайно передать килограммы или повторения туда, где ждут фунты. Значение получается только через схему, без приведения типов.
- **Время** только через порт часов: тесты смены недели и перехода на зимнее время детерминированы.
- **Данные неизменяемы:** `.readonly()` в схемах, никаких мутаций входных аргументов.
- **Никаких `any` и `as`** в ядре (проверяет architecture test), `strict` в `deno.json`.
- **Имена файлов** — kebab-case, один модуль — одна ответственность.

### 13.6. Тулчейн: Deno везде

Edge Functions работают на Deno, поэтому и разработка, и тесты тоже на Deno: один рантайм, нет класса ошибок «в тестах работает, в функции нет». npm-пакеты подключаются через `npm:` в import map `deno.json`. Команды — в README и `deno.json` (`tasks`).

Локальный рантайм Edge Functions может отставать от установленного Deno по версии: новые API Deno проверять через `supabase functions serve`.
