# Нефункциональные требования

## 9. Нефункциональные требования

**Надёжность записи**

- Каждый подход пишется в БД сразу, до подтверждения пользователю. «Записал» отправляется только после успешной записи.
- Идемпотентность: Telegram повторяет webhook при таймауте. Хранить `lastUpdateId` в `session` и игнорировать уже обработанные `update_id`. В `callback_data` кнопок передавать идентификатор шага, чтобы повторное нажатие на старую кнопку не создавало дубль.
- `answerCallbackQuery` на каждое нажатие, сразу.

**Скорость**

- Цель: ответ ≤ 500 мс на нажатие кнопки (p95), без холодных стартов. Приёмы — в разделе 3.
- Экспорт и LLM-вызовы могут быть дольше: сначала сообщение «⏳ Готовлю файл…», затем результат.

**Безопасность**

- Доступ: бот отвечает владельцам из `ALLOWED_USER_IDS` (переменная окружения) и участникам, которых они пригласили (product.md → US-9). Остальным — тишина; единственное исключение — ответ «приглашение недействительно» на `/start` с кодом. Только личные чаты, группы игнорируются.
- Приглашение: код из случайного UUID (122 бита), одноразовый, срок 7 дней; использование кода и добавление участника — одной транзакцией, повторное использование невозможно.
- Проверка заголовка `X-Telegram-Bot-Api-Secret-Token` (задаётся при `setWebhook`).
- Секреты (`BOT_TOKEN`, `WEBHOOK_SECRET`, `CRON_SECRET`, `DEEPSEEK_API_KEY`) — через `supabase secrets set`; секрет для вызовов из GitHub Actions — в GitHub Secrets. В коде и репозитории секретов нет.
- RLS включён на всех таблицах без политик: через публичный API Supabase данные недоступны, пишет только функция `bot`. Функция задеплоена с `--no-verify-jwt`, поэтому эндпоинты `/webhook` и `/health` сами проверяют свой секрет в заголовке.
- Репозиторий публичный: в нём нет секретов, дампов, выгрузок и реальных данных тренировок (фикстуры — только синтетические). Логи GitHub Actions тоже публичны, поэтому workflow не печатает содержимое БД и ответы бота; секреты передаются только через GitHub Secrets.

**LLM (фаза 2)**

- Все ответы LLM — строгий JSON, валидируемый zod. При невалидном ответе — один ретрай, затем «Не понял, введи в формате 185x8».
- LLM никогда не пишет в базу напрямую: результат всегда показывается с кнопкой подтверждения.
- Провайдер задаётся переменными окружения (`LLM_BASE_URL`, `LLM_MODEL`).
- Данные уходят стороннему провайдеру: для тренировочных логов приемлемо, упомянуть в README.

**Качество кода**

- `strict` в `deno.json`, `deno lint` и `deno fmt`, `deno task check` = fmt + lint + typecheck + tests + проверка правила зависимостей (раздел 13).
- Unit-тесты (`deno test`) на весь `core/`: округление, ступени разминки (фикстуры из раздела 6), ротация дней, часовые пояса (переход на зимнее время), парсер «185x8», автомат диалога (последовательности событий).
- Интеграционные тесты бота: сценарии из раздела 10 на локальном стеке Supabase (`supabase start` + `supabase functions serve`) с замоканным Telegram API.
- Локальная разработка: `deno task dev` в режиме long polling, без деплоя на каждую правку.

**Резервное копирование (обязательно: на бесплатном плане Supabase нет автоматических бэкапов).** Ежедневный дамп БД файлом в личный чат Telegram, схема в миграциях, процедура восстановления в `docs/runbook-restore.md` (подробности в разделе 3). Ежедневный workflow заодно не даёт проекту уйти на паузу. Выгрузка `.xlsx` делается только по команде `/export`.
